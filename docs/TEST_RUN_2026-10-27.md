What was actually run, on what, and what could not be run here. Nothing in this
file is marked passed because the code exists or because a unit test passed.

**Where this ran:** a Linux build container. No Windows desktop, no GPU, no

## Priority 1 — real AI inference: BLOCKED, with evidence

**How the provider is chosen.** `claw/config.py` holds `ModelSettings.mode`, one
of `builtin`, `cloud` or `custom`. `ClawState.think_adapter()` sends `cloud` and
`custom` to `build_adapter()` (`claw/models/registry.py`, which maps
`provider` to the Ollama or OpenAI-compatible adapter), and `builtin` to
`Brain.adapter()`, which picks the user's selected brain, else the largest
installed brain that fits the hardware, else nothing — and then starts
llama.cpp's `llama-server` on 127.0.0.1 with a per-launch key.

**Is a model usable here? No, and these are the checks:**

| Check | Result |
|---|---|
| `find_engine()` (the llama-server binary) | `None` — not bundled, not on PATH |
| `ModelStore.list()` (installed brains) | `[]` — nothing installed |
| huggingface.co, cdn-lfs.huggingface.co | connection refused by the egress proxy |
| github.com release assets | HTTP 403 from the egress proxy |
| Provider credentials in settings | none configured; inventing one is forbidden |

I tried to build `llama-server` from the llama.cpp source vendored inside the
`llama-cpp-python` sdist on PyPI (PyPI is reachable). cmake configured it; the
sandbox then refused to compile downloaded external code. Even with a binary,
there are no trained weights to load: every GGUF source is on a blocked host.

**So steps 3–6 of Priority 1 were not performed, and no result is claimed for
them.** No prompt was sent to any real model. The existing model tests use
`tests/fake_model_server.py`, which is labelled a test double in its own
docstring, and `tests/make_tiny_gguf.py` is random weights, not a usable model.

### What was improved instead (step 7)

1. **`/models/status` in builtin mode now reports `reason`.** It never did, so
   the interface could not tell "the llama.cpp engine is missing" from "no brain
   is installed" and fell back to generic wording. (`claw/api/app.py`)
2. **New `POST /models/selftest`.** `/models/status` and `/models/probe` only ask
   whether a server is there and whether it lists the model — neither generates
   anything, so both can say "Ready" for a configuration that fails the moment a
   task starts. `selftest` sends a real prompt and reports whether words came
   back, how long it took, and the model's own first 300 characters. It can test
   the saved configuration or an unsaved one from the Settings form, and it
   never needs the API key retyped.
3. **"Test connection" stopped overclaiming.** It used to print
   "Connected. <model> answered." after a check that generated nothing. It now
   runs the self-test and quotes the actual reply, or says plainly that the model
   did not answer. (screenshot: `build/screenshots/app-model-test-dark.png`)

## Priority 2 — the desktop toolchain

`launch_app`, `focus_window` and `press_keys` were read line by line. They are
in good shape: `launch_app` refuses system tools (cmd, PowerShell, regedit,
Windows Security, Control Panel) before touching the desktop, and waits for a
genuinely new window rather than assuming; `focus_window` re-reads the active
window afterwards and reports `verified=False` if something else stayed in
front; `press_keys` validates to exactly one main key from an allow-list,
refuses the Windows key and Ctrl+Alt+Del / Alt+Tab / Ctrl+Esc / Ctrl+Shift+Esc,
escalates Enter to DESTRUCTIVE inside messaging apps, and compares a before and
after snapshot so an error dialog is reported instead of being called success.

**Seven deterministic tests were added for the failure paths**, which nothing
covered before: no window appears after launch; a system tool refused before the
desktop is touched; focus refused by another window; an ambiguous window title;
an error dialog after a keypress; a keypress with no effect; typing that does not
read back. `LAUNCH_TIMEOUT_S` became a named constant so the failure path can be
tested in a second instead of fifteen.

**These run against `tests/fake_desktop.py`, a labelled test double.** They prove
the logic. They do not prove Windows UI Automation. All 26 desktop tests pass;
all six Windows desktop tasks remain BLOCKED.

## Priority 3 — web search: the environment, not the implementation

`web_search` builds the engine URL, navigates with the real browser, scrapes the
engine's result layout, and falls back to generic link extraction when the
layout has changed. The code path was exercised for real against a live local
search page (one result parsed from a real DOM).

A real attempt at `https://html.duckduckgo.com/html/?q=python` returns
`ERR_TUNNEL_CONNECTION_FAILED`. duckduckgo.com, bing.com, google.com, python.org
and example.com are all refused by the egress proxy. **The implementation is not
the problem; this container has no public internet.** The local-site tests remain
labelled as local-site tests.

Two real defects surfaced while proving that, and both are fixed:

- Chromium's raw error codes reached the user (`net::ERR_TUNNEL_CONNECTION_FAILED`).
  They are now translated to plain words with the code kept for a bug report —
  "this computer is not connected to the internet (ERR_INTERNET_DISCONNECTED)".
- After a navigation failed part-way, the *next* read of the page raised
  Playwright's own "Execution context was destroyed" as an unhandled error. It
  now raises a clean, actionable message. Found by a real failure, not by reading.

## What you have to run yourself

### A. The six Windows desktop tasks (3.1–3.6, and 1.4)

On the Windows machine, from the repository:

```powershell
cd backend
.\.venv\Scripts\python.exe -m pytest tests/test_desktop.py -q      # logic, still the double
```

Then the real thing, which no test can do for you — install Claw, open it, and
give it these one at a time, approving each step:

1. `Open Notepad`
2. `Open Calculator and work out 245 x 36`
3. `Open File Explorer at my Documents folder`
4. `Open <some picture>.jpg in the default image viewer`
5. `Switch to Notepad, then switch back`
6. `Open Windows Settings at the Bluetooth page`

For each one, note whether the window actually appeared and whether Claw's own
summary said `verified`. A summary that says "Started X, but no new window
appeared within 15 seconds" is the honest failure, not a crash.

### B. Real inference (Priority 1, steps 3–6)

**Local brain.** In Claw: Settings → Claw's brain → download the recommended
one (3.4 GB for the 4B, ~6 GB for the 8B), wait for it to verify, then:

1. Ask Claw: `Write a short professional email asking a supplier for a quote.`
   — that is the judgment task.
2. Ask Claw: `How many words are in <file>.txt?` — that is the tool-use task:
   the model has to request `count_text`, Claw validates and runs it, and the
   tool checks the answer against the file.
3. In Settings, press **Test connection** (or `POST /models/selftest`) and
   confirm it quotes an actual reply with a time.

**Hosted model.** Settings → Claw's brain → Online model, enter the address and
model of a provider *you* have an account with, paste your key, press **Test
connection**. It must quote the model's own words. I did not and will not invent
an endpoint, a model name or a key.

To check the engine tests that are skipped here, build or install `llama-server`
on that machine (`scripts\setup.ps1` does it) and re-run `pytest tests/test_runtime.py`:
the seven skips become real runs against the tiny random-weight model.

### C. Public web search (4.2)

On a machine with ordinary internet, ask Claw: `Search the web for the official
Python website and open the first result.` This is the only way to confirm that
the DuckDuckGo result-page scraping still matches DuckDuckGo's current markup —
the local stand-in cannot tell you that.
