============================================================
1. THE CORE STRATEGY
============================================================

Do NOT build 286 separate features from scratch.

Build a reliable desktop agent that:
1. Understands the user's request.
2. Identifies the intended outcome and constraints.
3. Selects a tested tool/adapter.
4. Executes through deterministic APIs wherever possible.
5. Uses GUI automation only when no stable API exists.
6. Verifies the actual resulting files, application state, or external outcome.
7. Reports exactly what succeeded, failed, needs approval, or remains incomplete.

S-CLAW should be the orchestrator and user experience. Existing libraries should do specialist work.

Preferred execution order:
A. Direct application API / command-line interface / file-format library.
B. Application scripting interface (for example Blender Python or LibreOffice UNO).
C. Accessibility/UI Automation tree (Windows UIA).
D. Screenshot + OCR + visual grounding.
E. Raw mouse/keyboard coordinates only as a last resort.

Do not use an LLM to calculate arithmetic, manipulate pixels, transcode media, parse spreadsheets, or perform other deterministic work when a reliable library already exists.

IMPORTANT PRODUCT CONSTRAINTS:
- Windows 10/11 desktop application remains the product.
- Do not turn S-CLAW into a web chatbot.
- Do not make Ollama a required dependency.
- Do not require end users to provide API keys.
- Prefer free/open-source components and zero-cost local execution.
- Keep low-spec PCs in mind. Do not install every large dependency on every machine.
- Support optional capabilities and detect whether their required application/tool is installed.
- Do not silently upload user files to cloud services.
- Ask before destructive, external, financial, account, or irreversible actions.
- Keep current working functionality. Do not rewrite the whole architecture to adopt a repository.

2. REPOSITORIES AND TOOLS TO EVALUATE
============================================================

These are candidate upstream projects, not instructions to blindly clone them. Inspect each README, release history, Windows support, license, dependencies, security posture, and maintenance before adoption. Prefer released versions and pinned commits/tags over main/latest in production.

A. WINDOWS DESKTOP AUTOMATION — HIGH PRIORITY

1) pywinauto
GitHub: https://github.com/pywinauto/pywinauto
Use for: Windows desktop application control through Win32 and Microsoft UI Automation (UIA); finding controls by names/text; clicking buttons; entering text; reading UI state.
Why: Much more reliable than hard-coded screen coordinates when applications expose accessibility controls.
Suggested use: Make this the first GUI adapter for Notepad, Calculator, File Explorer, Settings, and supported desktop apps.
Caution: Some apps expose poor UIA trees. Use timeouts, inspect control identifiers, and fall back deliberately.

2) Browser Use (open-source Python library)
GitHub: https://github.com/browser-use/browser-use
Use for: AI-assisted multi-step browser workflows.
Why: It provides an existing browser-agent implementation instead of building every browser interaction from zero.
Caution: The repository also offers paid hosted services. Use only the local/open-source path if keeping costs at zero. Confirm which model/provider path is actually free; do not assume the hosted model is free. Review data handling before connecting authenticated accounts.

3) Playwright
GitHub: https://github.com/microsoft/playwright
Use for: Deterministic browser automation, page navigation, locators, form filling, downloads, screenshots, and browser tests.
Why: Prefer Playwright for repeatable known web workflows; use an AI browser agent only for ambiguous pages or workflows.
Suggested use: Build a Playwright adapter with role/text/label locators, explicit waits, download handling, and screenshots on failure.
Caution: Browser automation does not automatically bypass CAPTCHAs, MFA, access controls, or website terms. Never promise that it does.

B. IMAGE, OCR AND DOCUMENT VISUAL PROCESSING

4) OpenCV
GitHub: https://github.com/opencv/opencv
Use for: Image transformations, thresholding, masking, contours, image comparison, perspective correction, blur/sharpness checks, basic computer vision.
Suggested use: Image-processing adapter for supported Photoshop-like tasks. Combine with Pillow.
Caution: OpenCV is not a generative image model and cannot reliably reconstruct arbitrary missing backgrounds by itself.

5) Pillow
GitHub: https://github.com/python-pillow/Pillow
Use for: Image open/save, resize, crop, compositing, text, formats, thumbnails, basic image editing.
Suggested use: Use for deterministic image operations and output generation.

6) Tesseract OCR
GitHub: https://github.com/tesseract-ocr/tesseract
Language data: https://github.com/tesseract-ocr/tessdata
Use for: Offline OCR, text extraction from screenshots and scanned images.
Suggested use: Existing OCR layer should expose confidence, bounding boxes, language selection, and preprocessing.
Caution: OCR accuracy depends heavily on image quality and language data. Keep the current tested OCR path unless a benchmark proves an alternative is better.

C. VIDEO AND AUDIO

7) FFmpeg
GitHub: https://github.com/FFmpeg/FFmpeg
Use for: Video/audio conversion, trimming, concatenation, resizing, codecs, subtitles, extracting audio, probing metadata, audio mixing, filters.
Suggested use: Make FFmpeg the media-processing backend. Build tested command templates and validate outputs with ffprobe.
Caution: FFmpeg has multiple license configurations (LGPL/GPL depending on build options). Check the exact build and redistribution obligations before bundling it in a commercial installer.

8) whisper.cpp
GitHub: https://github.com/ggml-org/whisper.cpp
Use for: Offline speech-to-text, including Windows builds and CPU inference.
Suggested use: Evaluate as an optional local speech-recognition backend. Benchmark small quantized models on low-spec PCs before selecting defaults.
Caution: Model downloads are separate from source code and have their own sizes/licenses. Do not promise real-time performance on every 4 GB PC.

D. SPREADSHEETS, DATA AND OFFICE DOCUMENTS

9) pandas
GitHub: https://github.com/pandas-dev/pandas
Use for: CSV/Excel data cleaning, joins, grouping, deduplication, analysis, data transformations.
Suggested use: Data engine for challenges 7.x and 13.x. Use deterministic code and preserve original source data.

10) openpyxl
Official project: https://foss.heptapod.net/openpyxl/openpyxl
GitHub mirror (not the preferred canonical upstream): https://github.com/ericgazoni/openpyxl
Use for: Reading/writing Excel .xlsx files, sheets, cells, formulas, formatting, charts.
Suggested use: Use the official project source and documentation; do not base adoption on an old mirror.
Caution: It does not calculate Excel formulas. Preserve formulas and, when calculation is needed, use a compatible spreadsheet engine.

11) python-docx
GitHub: https://github.com/python-openxml/python-docx
Use for: Creating and editing .docx files, paragraphs, tables, styles, headers, footers.
Suggested use: Document generation and basic formatting.
Caution: Complex Word layout, fields, tracked changes, advanced page layout, and exact rendering may require LibreOffice/Word automation and visual validation.

12) python-pptx
GitHub: https://github.com/scanny/python-pptx
Use for: Creating and editing PowerPoint .pptx presentations, slides, shapes, text, images, tables, charts.
Suggested use: Generate presentations from structured content.
Caution: It does not provide full PowerPoint editing/rendering or rich animation authoring. Verify exported slides visually.

13) LibreOffice
GitHub: https://github.com/LibreOffice/core
Use for: Free office suite and headless document conversion/rendering; can serve as a local office engine.
Suggested use: Detect an installed LibreOffice instance and use headless conversion/export for DOCX, XLSX, PPTX and PDF workflows where supported. Investigate UNO scripting for deeper automation.
Caution: Do not assume perfect Microsoft Office compatibility. Test fonts, pagination, formulas, charts and slide rendering.

E. 3D AND ENGINEERING

14) Blender
GitHub: https://github.com/blender/blender
Python API documentation: https://docs.blender.org/api/current/
Use for: Scripted 3D scenes, materials, cameras, animation, rendering and asset manipulation.
Suggested use: Generate .py scripts and run Blender in background mode when installed. Validate output files and render previews.
Caution: Heavy for low-spec PCs; make it optional. Advanced modelling still requires strong planning and verification.

15) FreeCAD
GitHub: https://github.com/FreeCAD/FreeCAD
Use for: Parametric CAD, mechanical models, technical drawings and Python scripting.
Suggested use: Create scripts/macros using FreeCAD's Python API for constrained, well-specified CAD tasks.
Caution: CAD correctness requires geometric and dimensional validation. Do not claim SolidWorks/AutoCAD parity.

F. COMPUTER-USE BENCHMARKING

16) OSWorld
Project: https://os-world.github.io/
GitHub: https://github.com/xlang-ai/OSWorld
Use for: Research benchmark and reproducible evaluation of computer-use agents across desktop and browser applications.
Suggested use: Study its task setup, execution evaluation and reproducibility. Adapt selected tasks to S-CLAW's Windows test lab.
Caution: Full OSWorld infrastructure may be heavy. Do not make it a runtime dependency.

17) OSWorld-V2
GitHub: https://github.com/xlang-ai/OSWorld-V2
Use for: Newer long-horizon computer-use evaluation ideas.
Suggested use: Study its current versioned evaluation workflow and task design. Pin a release; do not mix task assets and code from different versions.
Caution: Treat as a benchmark/reference, not a library to bundle into the desktop app.

Do not attempt all categories at once. Work in this order:

PHASE 4 — MEDIA AND DESIGN
- Pillow + OpenCV for image manipulation.
- FFmpeg for video/audio pipelines.
- Tesseract for OCR.
- whisper.cpp as optional offline speech recognition.

PHASE 5 — CAD AND ENGINEERING

Deliverable: limited, clearly scoped engineering workflows; do not claim broad CAD parity.

PHASE 6 — MULTI-APP MISSIONS
Only after individual adapters pass:
- Advertising campaign
- Software product workflow

Each mission must have setup, preconditions, action log, output assertions and cleanup.

6. Stop if instructions conflict or if the requested action exceeds permissions.
7. Never mark success until verification passes.

5. TESTING RULES — NON-NEGOTIABLE
============================================================

A test is not passed because:
- the model said it completed;
- a function returned without throwing;
- a script was generated;
- a window was clicked;
- an output file exists but is empty or corrupt.

A test passes only when an independent assertion confirms the intended result.

For every challenge, record:
- challenge ID
- environment and Windows version
- machine specs (RAM, CPU, GPU)
- required application/tool versions
- model/provider and model configuration
- initial state and input files
- exact user instruction
- planned actions
- actual actions
- output artifact paths
- independent verification assertions
- screenshots/logs where useful
- pass/fail/partial
- known limitations
- reproducible command

Use three test levels:
1. Unit tests: individual functions and adapters.
2. Integration tests: adapter + real application/library.
3. End-to-end tests: real task from natural-language request to verified outcome.

Use a clean Windows VM or physical Windows test PC for real desktop claims. A Linux test run cannot prove Windows GUI behavior.

For reliability:
- Pin dependency versions.
- Add timeouts to every external process and UI wait.
- Capture stderr/stdout.
- Handle process crashes and partial outputs.
- Use temporary workspaces and test fixtures.
- Make tests repeatable and safe.
- Test both success and failure paths.
- Run existing tests before and after every change.
- Do not remove or weaken an existing test merely to get a green build.

============================================================
6. SECURITY, PERMISSIONS AND USER TRUST
============================================================

S-CLAW controls a real computer. Treat this as a security-sensitive system.

Require explicit approval before:
- deleting or overwriting user files;
- sending emails, WhatsApp messages or other communications;
- submitting external forms;
- purchasing, transferring money or changing financial data;
- installing/uninstalling software;
- changing security settings, permissions or startup behavior;
- uploading files to external services;
- executing commands with administrator privileges.

Never:
- log passwords, cookies, tokens or private message contents unnecessarily;
- execute untrusted repository scripts without inspection;
- run arbitrary shell commands generated by a model without policy checks;
- silently switch from local processing to cloud processing;
- claim a task is complete if verification failed.

Use least privilege. Keep a clear audit trail and allow cancellation.

============================================================
7. HOW TO HANDLE THE CHALLENGE LIST
============================================================

Do not treat every PLANNED or OUT item as a coding task.

For each challenge:
1. Identify the true user outcome.
2. Determine whether a free tool/library can achieve it.
3. Determine whether the required external application/account is installed/available.
4. Classify it:
   A. Deterministic library/API task.
   B. Application scripting task.
   C. GUI automation task.
   D. Model-dependent creative/reasoning task.
   E. Requires paid software/account or unavailable capability.
5. Select the smallest reliable implementation.
6. Add a benchmark and independent verifier.
7. Run it on the required environment.
8. Update status only according to TEST_RESULTS.md evidence.

Important examples:
- Spreadsheet deduplication should be a deterministic data operation, not an AI mouse-click workflow.
- Video trimming/concatenation/subtitles should use FFmpeg where suitable.
- OCR should use the existing OCR engine and image preprocessing.
- A browser price comparison should use Playwright locators and structured extraction where possible.
- A complex unfamiliar GUI task may require UIA plus vision and model reasoning.
- Removing a person from a crowded photograph with natural background reconstruction is not solved merely by installing OpenCV. Keep it OUT unless a suitable model/tool and licensing/compute plan are verified.
- Figma account-dependent tasks should not be silently represented as locally solved design tasks.
- SolidWorks/AutoCAD-specific file compatibility should not be claimed just because FreeCAD can perform some CAD operations.
